# 算法实验与优化平台

> 文档状态：当前代码能力说明（2026-09-20）  
> 实现范围：`experiment/algorithm_platform`、`experiment/algorithm_platform_plugins/dfjsp_t`、`application/backend/algorithm_platform_routes.py` 与前端 `/training` 工作台  
> 验证边界：本文按已落地代码更新；本次文档修订未运行测试、构建或算法效果验收。

## 1. 平台定位

平台统一承载算法训练、超参数探索、数据集测试、结果比较和过程回放。强化学习、启发式算法、精确求解器和参数搜索算法都可以通过各自的运行接口接入同一工作流。

平台当前统一管理：

- 不可变实验定义和稳定内容摘要；
- 版本化算法、领域与 Runtime 能力目录；
- Experiment、Execution、Trial、Run 四层执行对象；
- 正式领域给出的观测、动作校验、状态推进与客观指标；
- 训练产物、参数候选、封闭测试和公平比较；
- 只追加事件、内容寻址制品、执行清单与回放证据；
- 记录回放、确定性复现、快照分支和双 Run 差异诊断；
- HTTP 控制面和独立算法实验工作台。

## 2. 核心层级

```text
Experiment：不可变研究意图
└── Execution：一次实际启动及其状态
    ├── Trial A：算法版本 + 一组确定参数
    │   ├── Run：场景 1 × seed 1 × repetition 1
    │   └── Run：场景 2 × seed 2 × repetition 1
    └── Trial B
        └── ...
```

- Trial 是参数候选或算法变体的评价单元。
- Run 是一个场景、分离 seed 和重复编号上的最小可复现执行单元。
- Episode、Generation、Iteration 是 Run 内部事件，不是平台基础层级。
- Artifact 可为模型、参数、checkpoint、完整方案、执行计划、事件日志、状态快照、报告或数据集。

实验定义以 `experiment_id` 为不可变标识。同一标识再次保存相同内容会返回原记录；内容改变时必须使用新的标识。确定性复现和快照分支不会伪造新的 Experiment，而是以 `purpose=replay` 保存为源 Experiment 下的子 Execution，并记录源 Execution、源 Run、算法版本和回放模式。

## 3. 已实现的执行模型

平台使用分离协议，不设置万能算法基类。

| 接口 | 当前默认 Runtime | 典型算法 | 执行方式 |
|---|---|---|---|
| `online` | `OnlineRuntimeDriver` | SPT、EDD、滚动时域 GA、冻结 PPO 策略 | 观测—决策—校验—执行—反馈循环 |
| `batch` | `BatchRuntimeDriver` | CP-SAT、MILP | 输入完整问题，校验并评价完整方案 |
| `iterative` | `IterativeRuntimeDriver` | GA、PSO、SA、ACO | 候选提出、领域评价、incumbent 更新 |
| `trainable` | `TrainableRuntimeDriver` | CTDE-PPO、监督/模仿学习算法 | 训练产生不可变产物，再在领域数据上评价 |
| `search_optimizer` | `TuningOrchestrator` 驱动 | 网格、随机、遗传参数搜索 | `ask/tell` 动态生成并评价 Trial |
| `plugin` | 显式注册的 RuntimePlugin | 新执行范式 | 由算法 Manifest 选择精确 Runtime 版本 |

算法 Manifest 声明接口、支持领域、参数 schema、输入/输出制品种类、每种接口的 `minimum_input_artifacts` 及可选 Runtime。编译和快照分支都会按所选接口检查最少输入制品数；例如冻结策略可以声明在线推理至少需要一个模型制品。配置文件只引用已注册的 ID 和版本，不接受可执行 import target。

## 4. 实验编译与执行

标准实验流程为：

```text
JSON/YAML ExperimentSpec
  → schema、领域能力、目标、预算与数据分区校验
  → 确定性编译 Trial/Run 矩阵
  → 生成稳定 trial_id、run_id 和 plan_digest
  → LocalOrchestrator 按计划顺序执行
  → RunResult、事件日志、制品与 Manifest
  → Trial 聚合或统一比较报告
```

V1 配置只支持 `schema_version=1`；显式给出其他版本会被拒绝，未填写时按版本 1 读取。Experiment 顶层字段采用白名单，未知顶层字段直接报错；算法和领域参数则继续按注册 Manifest 的 schema 校验。

`purpose=tune` 不预先展开固定 Trial 矩阵，而由 `TuningOrchestrator` 在执行期动态生成候选。HTTP `/compile` 对这类实验返回 `dynamic=true` 和稳定定义摘要。

Execution 控制面持久化 `draft → compiled → running → succeeded/failed`，以及 `compiled/running → cancel_requested → cancelled` 状态。HTTP 路由负责创建并在守护线程中启动 Execution，也提供协作式取消端点。取消信号会传入 `RunContext`，编排器在 Run 边界检查，Online、Iterative 和调优循环在迭代边界检查，DFJSP-T PPO 也在训练循环内主动检查；它不会强杀线程或中断第三方求解器的一次阻塞调用。

一个 Run 在 Runtime 执行阶段抛出异常时，平台会把该 Run 记录为 `failed`，保留结构化 `RunFailure`、结束事件、事件日志和报告，然后继续执行计划中的后续 Run。编译、制品完整性或 Runtime 构造等执行前错误仍会使整个 Execution 失败。服务重启时，无法继续的本进程状态会被收口：遗留 `cancel_requested` 变为 `cancelled`，遗留 `draft/compiled/running` 变为 `failed`。

## 5. 超参数探索

当前已注册三种平台内置调优器：

- `platform.grid_search@1.0.0`；
- `platform.random_search@1.0.0`；
- `platform.genetic_search@1.0.0`。

搜索空间支持 `categorical`、`integer` 和 `float`。调优器按批次 `ask` 候选，平台把每个候选转成独立 Trial，在相同调优场景、seed 与重复次数上执行，再把正式聚合结果 `tell` 回调优器。

调优数据边界由编译器强制：

- `scenarios` 用于候选选择；候选评价子实验明确使用 `purpose=validate`；
- 可训练目标必须另外提供且只能提供一个 `training_scenarios` 语料场景；
- 必须提供 `benchmark_scenarios`；
- 三部分的场景 ID 和摘要必须互斥；
- 候选选择场景和训练场景不得声明 `metadata.split=benchmark`，Benchmark 场景必须显式声明该 split；
- Benchmark 只评价最终 incumbent，不参与候选选择；
- DFJSP-T 领域会拒绝把声明为 benchmark 的语料用于训练或验证。

调优结果保存候选结果、incumbent、训练/评价/Benchmark 子 Execution、优化器 checkpoint、事件日志和汇总报告。单个候选的训练或评价 Run 失败时，该候选以 `TrialStatus.FAILED` 回传给优化器，搜索继续；失败候选不参与 incumbent 选择。仅当所有候选都失败、没有可选 incumbent 时，调优 Execution 才失败。Pareto 目标可保留多个非支配 incumbent。

## 6. 指标、目标与数据集比较

平台严格区分：

- TrainingSignal：算法内部训练信号；
- Metric：领域客观记录；
- Objective：由 Metric 构成的比较规则；
- Fitness：调优器接收的 Trial 聚合结果。

目标支持：

- 单目标 `single`；
- 加权和 `weighted_sum`；
- 词典序 `lexicographic`；
- Pareto `pareto`；
- `lt/le/eq/ge/gt` 约束、容差及可行性优先；
- `mean/median/min/max/sum/last` 跨 Run 聚合。

底层协议仍能为受控实验生成配对比较报告；V1 工作台不再把“比较”作为实验模式。用户先以“测试”模式把固定算法和固定参数运行在所选测试集上，统一比较页再按数据集汇总已经完成的测试结果，包括覆盖实例数、成功运行数、平均 `C_max_E`、平均 `C_max` 和最近测试时间。

底层配对比较报告可校验所有算法具有相同的场景摘要、重复编号、环境 seed、实例 seed 和外生 seed 单元，并给出：

- 每个算法的 Run 完整性与状态统计；
- Metric 和 Objective 的描述统计；
- 排名或 Pareto 层；
- 两两配对胜/平/负、目标差异和双侧符号检验结果；
- 是否为平衡且完整的比较设计。

DFJSP-T 推荐正式比较规则为：有特急订单时按 `(C_max_E, C_max)` 词典序最小化；无特急订单时只使用 `C_max`。

## 7. 事件、制品与回放

每个 Run 产生只追加 JSONL 事件流。平台事件包括运行开始/结束、训练与评价、调优候选、Benchmark、观测、决策、动作校验与执行、状态变化、指标、快照和制品等。

当前三类回放已经落地：

1. **记录回放**：读取不可变事件日志，可切换完整事件或决策聚合视图，并返回回放就绪度诊断。
2. **确定性复现**：加载持久化 RunSpec，以相同算法/领域版本、场景和 seed 重跑，再按策略比较序号、时间、负载和状态 hash。
3. **快照分支**：从正式状态快照恢复，替换为另一个已注册 `online` 算法继续执行，生成新的 Trace 和来源清单。

`ReplayDiffer` 还支持比较任意两个 Run，配置浮点/仿真时间容差、事件类型过滤、忽略负载路径、状态 hash 开关和最大差异数。

`record_replay_ready`、`deterministic_replay_ready` 和 `branch_replay_ready` 表示相应事件、计划或快照证据是否齐全，不承诺当前机器仍具备源数据、算法依赖或可执行环境。真正发起复现或分支时，平台还会再次检查版本、计划、参数 schema、输入制品和快照摘要。记录回放返回的 `factory_config` 只是前端正式工厂渲染的可选便利数据；源场景不可读、已变更或是语料场景时可以为 `null`，事件回放仍可使用。

制品使用 SHA-256 内容寻址存储。Run、Execution、调优和回放分别发布 Manifest；读取输入和快照时会做摘要完整性校验。

## 8. DFJSP-T 正式插件

`experiment/algorithm_platform_plugins/dfjsp_t` 已注册：

| 类型 | 注册 ID | 接口 |
|---|---|---|
| 领域 | `dfjsp_t@1.0.0` | online、batch、training data、snapshot restore、deterministic replay |
| 规则 | `spt_rule@1.0.0` | online |
| 规则 | `edd_rule@1.0.0` | online |
| 可调规则 | `weighted_dispatch_rule@1.0.0` | online |
| 元启发式 | `rolling_ga@1.0.0` | online |
| 精确参考 | `cp_sat_reference@1.0.0` | batch |
| 学习算法 | `ctde_ppo@1.0.0` | trainable、online |

DFJSP-T 在线会话由 `SimulationSession.from_config(..., headless=True)` 创建，使用正式工厂状态转移；领域负责场景摘要校验、实例 schema 校验、动作合法性、正式指标、运行帧、状态 hash、快照发布和恢复。

领域侧保持以下业务边界：

- 订单在释放时刻前不可见；
- 在线算法不读取未来订单与未来故障；
- 只有特急订单可抢占正在加工的普通订单；
- 特急订单之间不互相抢占；
- 已完成加工和运输状态不回滚。

场景既可指向单个 JSON 实例，也可通过 `metadata.corpus=true` 指向带文件 SHA-256 的 JSONL 语料。训练语料需声明 `split=training`；验证语料由领域参数 `validation_scenarios` 显式配置。

## 9. HTTP 控制面与前端工作台

FastAPI 路由前缀为 `/algorithm-platform`，前端默认通过 `/api/algorithm-platform` 调用。控制面已提供：

- 能力目录；
- 数据集目录、数据集实例与按数据集索引的测试结果；
- 实验校验、编译、保存与读取；
- 异步创建 Execution、状态列表与详情；
- `POST /executions/{execution_id}/cancel` 协作式取消；
- Run、Metric、标准事件、Manifest 和比较报告；
- 记录回放、确定性复现、快照分支、双 Run Diff；
- 按 digest 下载制品。

项目内 HTTP 细节见《算法实验平台 HTTP API》。

独立工作台位于 `/training`，包含四个区域：

1. 定义实验：在训练、超参数探索、测试三种模式中选择数据集、算法和参数；超参数探索模式下可另外选择网格、随机或遗传搜索方式；
2. 执行监控：轮询 Execution，展示 Run 指标、候选、Benchmark 和事件；
3. 统一比较：选择测试数据集，汇总所有已在该数据集上完成测试的算法结果；
4. 回放诊断：选择数据集后列出其全部实例；已有测试结果的实例可继续选择算法运行记录。也可按执行记录选择已开始或已完成的 Run，然后使用记录/决策视图、正式工厂帧播放、确定性复现、快照分支和 Diff。

页面在浏览器 100% 缩放下使用独立纵向滚动，不会因工作台内容较长而遮挡底部功能。运行消息固定在页签下方的页面位置，不会吸附并跟随滚动。完整实验配置默认收起，点击“查看完整配置”后才显示 JSON；快照分支中的算法参数也采用相同的名称和值编辑方式，并保留“查看完整参数”入口。执行详情中的模型、检查点、调度方案和报告统一显示在“输出文件”区域。

工作台只提供三个实验模式：

- **训练**：优化算法内部模型参数并保存模型，只允许选择声明了 `trainable` 接口的算法。CTDE-PPO 保留更新模型所需的数据，每轮更新后释放采样数据，并分别记录采样与网络更新耗时；查看工厂运行过程时，可将模型用于独立测试和回放；
- **超参数探索**：搜索算法的外部配置参数。可训练算法会先在训练集拟合，纯启发式算法不经过拟合，但两者都在独立调优集上选择候选并在测试集做最终评价；
- **测试**：不修改模型或超参数，使用固定算法和固定参数在所选测试集全部实例上运行，并保存指标、输出文件和回放事件。

数据集不再隐含在按钮模板中。页面会读取后端数据集目录，并把所选数据集的 URI、文件摘要、实例 ID 和实例摘要写入实验定义。训练语料以 corpus 引用传入，调优和测试数据集展开为具体实例引用。

通过页面切换模式、算法、数据集或参数时，工作台会为变更后的定义生成新的 Experiment ID，避免同一不可变 ID 被不同内容重复使用。直接编辑完整 JSON 时仍由使用者维护该 ID。

能力目录中的“算法”只展示实际被训练或运行的算法。参数搜索优化器不再混入算法列表，而是在超参数探索模式下作为“参数优化方式”选择；当前提供网格搜索、随机搜索和遗传搜索。选择新的目标算法时，页面会按其参数 schema 生成可编辑的外部参数搜索范围，数值上下限、步长或离散候选值可直接修改。

“校验”用于检查配置是否合法；“编译计划”在此基础上生成实际执行结构。训练和测试会展开为确定的参数候选与运行单元，固定场景、重复编号、随机种子、算法版本和运行标识，并生成计划摘要，但不会立即开始运行或保存实验。超参数探索的候选需要在执行过程中由优化方式动态提出，因此编译阶段只完成校验并生成稳定定义摘要。

纯启发式算法不能进入训练模式，但可以进入超参数探索模式。例如加权派工规则可搜索加工时间、交付期、剩余工作量和优先级等外部权重，在调优数据集上选择候选，再用独立测试数据集完成最终评价。

CTDE-PPO 在训练和超参数探索模式下会选择 `trainable` 接口；在测试模式下选择 `online` 接口。这样训练请求不会再因误选在线接口而触发“train experiments require the trainable interface”。

CTDE-PPO 的“并行采样环境数”默认 4，可按机器资源调整；设为 1 时仅运行一个采样环境。“训练轮数”表示全部环境合计的采样回合数。例如训练 10 轮、并行环境数 4、验证间隔不小于 10 时，按 4、4、2 个回合分批采样和更新。进度消息分别显示各回合采样情况与整批网络更新阶段，训练输出继续用于独立测试和回放。

冻结 PPO 在线测试需要训练产生的模型或 checkpoint。训练完成后可在执行详情的输出文件上点击“用于测试”，页面会生成带输入文件引用的 PPO 测试配置；确认测试数据集后即可提交。

`GET /executions/{id}/runs` 对标准 Execution 的 `execution_id`、`owner_execution_id`、`route_execution_id` 和 `workspace_execution_id` 相同；对调优子 Run，前三者指向用户提交的根 Execution，`workspace_execution_id` 指向实际训练、候选评价或 Benchmark 子工作区。回放路由使用 `route_execution_id`，制品来源与排障使用 `workspace_execution_id`。

在工作空间选择页点击“算法实验与优化平台”进入工作台，该卡片位于原强化学习平台的位置。训练、超参数探索和测试统一在这里管理，也可直接访问 `/training`。

### 训练 Checkpoint

“Checkpoint 保存间隔”以所有采样环境累计的训练步数为单位，默认 0：只保留最佳 checkpoint。设为正数后，会在跨过该步数间隔后的第一次网络更新完成时保存中间 checkpoint，同时保留最佳 checkpoint。例如间隔 5000、每批实际采样 4000 步，会在累计 8000、12000 等跨过间隔的更新完成后保存；一个批次只保存一次该版本。

最佳 checkpoint 根据实验目标在固定评估场景上比较，优先使用验证数据集，未配置验证集时使用训练集评估。首次完成一批更新后建立最佳记录，随后按验证间隔比较并替换最佳记录。

执行详情的“训练 Checkpoint”会在训练过程中列出已保存的最佳和中间 checkpoint，可下载、用于测试或继续训练。继续训练时保留已完成轮数、累计步数、优化器和随机状态；“训练轮数”仍表示目标总轮数，必须大于 checkpoint 已完成轮数。服务意外重启后，可以从已保存 checkpoint 新建一次继续训练。

## 10. 持久化位置

后端默认使用 `dataset/algorithm_platform`：

```text
dataset/algorithm_platform/
├── experiments/       # 不可变实验定义
├── execution_state/   # Execution 状态快照
├── executions/        # 标准与回放 Run 工作目录、events.jsonl
├── tuning/            # 调优主事件日志
└── artifacts/         # 内容寻址对象与 Manifest
```

## 11. 当前边界

以下内容没有被描述为已完成：

- **没有分布式调度器。** `LocalOrchestrator` 在单进程内按稳定顺序执行 Run；HTTP 后台线程只让请求异步返回，不提供多机或队列调度。
- **没有 CPU/GPU/内存硬资源隔离。** 当前本地编排器会拒绝有效 Run 预算中的 `cpu_cores`、`gpu_count`、`memory_bytes`，而不是据此创建容器、cgroup 或独占设备。平台侧 wall time 主动检查只覆盖 Online、Iterative 和调优主循环；Batch 与 Trainable 不由平台计时中断。
- **当前 CTDE-PPO 尚未启用分布式训练。** 本机并行采样通过“并行采样环境数”控制；`distributed` 仍是多卡训练预留选项，不会启用多卡梯度同步或跨机器调度。
- **backend 支持自动选择 CUDA 或 CPU。** `install.sh` 和 Windows/Linux 启动脚本会在 backend 镜像内用 PyTorch 探测 Docker 可用设备；探测成功时叠加 `docker-compose.gpu.yml`，否则在 `auto` 模式回退 CPU。当前 PPO 仍是单卡训练，只使用实验参数 `gpu_ids` 中的第一张卡。
- **取消是协作式而非抢占式。** 平台不会强杀执行线程；Batch 求解、Trainable `fit/evaluate` 或第三方库的一次长阻塞调用，只有返回到检查点或算法自行读取 `RunContext.cancel_event` 后才会停止。
- **没有认证、授权或租户隔离。** 当前控制面适合受信任的本地或内网环境。
- **没有算法效果结论。** 代码具备运行、调优、比较与回放链路，不代表任一算法已收敛、优于基线或通过生产验收。
- **本次未运行验收。** 文档中的“已实现”只表示代码路径已存在并接通，不表示本轮执行过测试、构建、真实数据运行或 GUI 验收。
